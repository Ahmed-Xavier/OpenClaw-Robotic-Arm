We decided to add Laya as a fast System-1 routing layer.

## TARGET ARCHITECTURE

```
                     ┌── simple ──→ validation → RobotAPI
                     │
```

USER → LAYA ─────────────┤
│
└── complex → Qwen
↓
simple actions
↓
Laya
↓
validation → RobotAPI

The important point:
Laya is NOT replacing Qwen.

Laya decides whether the user's request is a simple robot action or a
complex task that needs Qwen's planning/reasoning.

Qwen then decomposes complex tasks into simple actions.

Those actions should still pass through Laya and the existing validation
layer before reaching the robot.

2. LAYA INVESTIGATION
=====================

We initially investigated the Laya project and found the public repository:

NandhaKishorM/laya

Laya describes itself as a multilingual, non-autoregressive System-1
decision engine.

It supports typed decisions such as:

* choice
* score
* noul

Available checkpoints include:

* laya
* laya-multilingual
* laya-typed-decisions

We cloned the repository and installed it locally.

Python environment:
Python 3.11.9

We initially had CPU-only PyTorch.

Detected hardware:
NVIDIA RTX 4050 Laptop GPU

We replaced CPU PyTorch with CUDA PyTorch:

torch 2.11.0+cu128
torchvision 0.26.0+cu128

CUDA is working.

The RTX 4050 is therefore being used for Laya inference.

==================================================
3. IMPORTANT LAYA DISCOVERY
===========================

We tested Laya's Router.

The Router added roughly 1.27 seconds of latency for a simple
"pick up the cube" request.

That is too much overhead for our intended fast System-1 layer.

Therefore:

DO NOT use Router.predict() for every robot command.

For our current English-only robot interface, use the direct Laya
checkpoint and keep it loaded in memory.

Direct Laya inference was measured around:

~140–240 ms

depending on the run.

The most recent end-to-end test measured:

240.25 ms

==================================================
4. CUSTOM ROBOT ROUTING QUESTION
================================

The generic Laya robot-unaware presets were not good enough.

Examples showed that generic classification could interpret things like
"pick up cube" or "move arm to cube" incorrectly.

Therefore we created a custom robotics question:

robot_action

with three choices:

simple_action
complex_task
non_robot

Definitions:

simple_action:
A single direct robot action that can be executed immediately.

complex_task:
A robot task requiring multiple actions or planning.

non_robot:
The request is not asking the robot to perform an action.

This custom question performed substantially better for basic robot
commands, although it is NOT perfect.

In particular, Laya sometimes confuses:
simple_action vs complex_task

and sometimes has difficulty with casual/non-robot requests.

Therefore Laya should NOT be treated as an absolute safety authority.

Existing validation + RobotAPI remain authoritative.

==================================================
5. LAYA CALIBRATION WARNING
===========================

Every load produces this warning:

"this checkpoint ships temperatures outside [0.5, 5] which would
distort confidence..."

Therefore:

DO NOT interpret Laya's probabilities as calibrated real-world
confidence percentages.

For example:

simple_action: 0.8259

does NOT necessarily mean:

"82.59% probability that this classification is correct."

The probabilities are still useful for comparing the model's output,
but they should not be treated as calibrated certainty.

==================================================
7. WHAT THIS TELLS US
=====================

Laya is NOT the main bottleneck.

For the tested pick action:

Laya:
~240 ms

Robot:
~1594 ms

Laya accounts for roughly 13% of the measured total time.

The actual robot action dominates the latency.

The earlier Router test was much slower because Router model selection
added significant overhead.

Therefore the intended implementation should keep the direct Laya
model resident in memory.

11. IMPORTANT DESIGN PRINCIPLE
==============================

The goal is NOT:

"Laya replaces Qwen."

The goal is:

"Laya handles fast System-1 decisions and routes complex work to Qwen."

The final architecture should preserve:

Laya = fast routing / decision layer

Qwen = complex reasoning / task decomposition

Validation = safety and schema enforcement

RobotAPI = final robot authority

MuJoCo = physical simulation
